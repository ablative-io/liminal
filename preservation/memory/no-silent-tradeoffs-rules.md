A comment explaining why a cost exists is documentation of a defect, not authorization for it.

Gate-integrity riders (2026-07-11 evening, from live incidents in others' lanes — adopt in my own practice regardless of pair ruling): (a) any step that can REWRITE bytes runs before every step that MEASURES them, or the measurement reruns (Apollo's fmt-after-clippy false green; my fmt --check is measure-only so unexposed); (b) gates count only on the FINAL bytes/head (Vesper's rebase rule; my merges already re-run on the merged tree); (c) TOOLCHAIN SKEW can make honest gates disagree (Artemis's clippy 1.94-vs-newer duplicated-cfg miss) — state rustc/clippy versions alongside exit codes in handoff packs; the reviewer-of-record's toolchain is authoritative.

(d) FRESHNESS (2026-07-12, Artemis's find, adopted house-wide by Apollo and me): a stale incremental fingerprint can serve a CACHED clippy pass on bytes that would fail a fresh run — it lied to Artemis's bar for a full round while she believed the gate green. **Touch the crate roots (`find crates -name lib.rs -o -name main.rs | xargs touch`) before every clippy gate**, and treat a suspiciously fast finish (sub-second "Finished dev profile") as an unexecuted gate, not a passing one. My own push-reply merge gate showed 0.09s = cached; re-run fresh on merged main 68379e8 was genuinely green (9.55s, all four crates analysed, exit 0) — the claim was true, the EVIDENCE was not sound, and that distinction is the whole point. State freshness beside the exit code and toolchain in handoff packs.

The governing law (Apollo's wording, worth keeping): **a gate that can lie is worse than a finding, because a finding stops you and a lie speeds you up.** Riders (a) and (d) are siblings — both are gates measuring something other than the bytes you think you're measuring.

## Tom's two board-binding rulings (2026-07-13 ~01:16Z; full text relayed verbatim by Waffles 2026-07-14 — the truncation gap is CLOSED)

**Ruling 1 — NO-POLLING: real-time is a design constant.** No application-layer poll loops anywhere in the product. Named consequences: the heartbeat option for no-FIN liveness is DEAD before it was drafted — crash detection stays event-driven (linked-EXIT in-VM, connection-fate cross-process), and the no-FIN bound is designed INSIDE that, not around it (this resolved the participant-contract §(b) collision, no options doc needed). Artemis's wasm pillar: setInterval-driven scheduler = the aion busy-spin reborn in a browser tab; F-0d acceptance requires event-loop-driven scheduling (run-to-idle, wake on message); a polling scheduler is a TEAR CONDITION, not a finding. Downstream: `frame dev` watches files by events never mtime loops; browser reconnect is event-driven never poll-retry; haematite-wasm syncs on commit events never periodic pulls. **The test: if a design has a timer whose job is "check whether something changed," it's wrong — redesign it to be TOLD.** The participant contract's LAW-1 is this ruling's enforceable shape (banned: timer/poll/sweep/scan/heartbeat/listener backoff/periodic reap/read-timeout wake/stop-flag sampling/synthetic state-change probes).

**Ruling 2 — SCAFFOLD THE WHOLE BOARD.** Paper-ahead-of-gates extends to ALL of v1, both poles, every unit to the end — paper clear enough that execution is mechanical. Every brief to the standard: numbered requirements, file:line evidence or named sockets, silence-attacking acceptance, no invented readiness, both laws stated where they bind.
