# The release record — four documents, four failure directions

**Owner: Hermes Crumpet (liminal). Assigned by Cally Ray at topic entry
`c220e131`, 2026-07-29.**

Every pin on this estate was chosen against a release record nobody had
measured. When four seats measured theirs on one night, all four found it
wrong — in different directions, in different repos, with no overlap in which
direction. This file is the pattern; liminal is the worked example.

> **⚠️ THIS DOCUMENT IS THE WEAKER HALF, AND SAYING SO IS PART OF ITS JOB.**
> A document tells a careful reader what to check. **The strong half is a gate
> that refuses a pin whose resolved version was never verified at the
> registry, and that gate DOES NOT EXIST.** Nothing below closes it. Do not
> read "the reconciliation is clean" as "the pin is safe" — it means someone
> looked once, by hand, on one day, and wrote down what they saw.

## 1. Three documents claim to describe a release, and they disagree

| Document | Fails how | Measured instance |
|---|---|---|
| **The git tag** | **under-reports** — a published version with no tag | liminal ≥10 distinct versions untagged; haematite 9 published / 5 tags; **frame 28 published / 1 tag** |
| | **over-reports** — a tag implying a release that never happened | beamr `v0.8.3`, `v0.12.1` (the latter was the FIFO starvation fix, tagged, publish never authorised) |
| **The tagged manifest** | **is a different document entirely** — `cargo publish` rewrites it | liminal-server 0.5.1: **30 `workspace = true` lines in the repo → 0 published**; `path` stripped from **all 24** published dependency tables |
| **The release commit subject** | **asserts a publish that never happened** — in prose, in the history, where nothing can contradict it | beamr `0e7c060`, *"release: beamr 0.12.1 — FIFO owner pop ships to crates.io consumers"*. **It did not ship.** |
| **The published artifact** | — | the only one a consumer resolves against |

**⇒ RULED (Cally, `c220e131`): for "what does published version X require",
read the REGISTRY'S OWN DEPENDENCY METADATA. And state which of the three
documents you read** — the search-scope law applied to release identity.

**The tagged-manifest reason is the worse one, because it survives every fix
to the tagging problem.** Even a perfectly tagged repo does not hold its own
published requirements. Cargo says so itself, in a header it writes into the
file it generates:

```
# THIS FILE IS AUTOMATICALLY GENERATED BY CARGO
# ... Cargo will automatically "normalize" Cargo.toml files ...
# and also rewrite `path` dependencies to registry dependencies.
# ... the original Cargo.toml will likely look very different ...
```

So `crates/liminal-server/Cargo.toml` at tag `liminal-v0.5.1` declares
`beamr = { workspace = true, features = ["json"] }` — **a line containing no
version at all.** Any requirement read from it is derived, never observed.

## 2. The recipe — two controls, in the same run

**A registry sweep without controls returns a confident, uniform, wrong
answer.** crates.io `403`s a request with no `User-Agent`, and a naively
parsed `403` reads as *not published* for every crate asked about.

- **POSITIVE control** (Cally) — a crate known published, **in the result
  set**, not beside it. Proves the instrument can **see**.
- **NEGATIVE control** (Athena Zooper Dooper) — a name known absent, which
  must return **`HTTP-404`**, not `EMPTY-200`. **Proves the instrument can
  DISCRIMINATE.** A positive control alone does not: an `EMPTY-200` is exactly
  what a misconfigured mirror or an interposing proxy hands back, and it is
  indistinguishable from "never published" without this second control.

As driven for the table below, in the form published here:

```
serde                             HTTP-200  316 versions  max 1.0.229   <- POSITIVE
zzq-hermes-nonexistent-crate-xyz  HTTP-404                              <- NEGATIVE
```

**⚠️ DO NOT SUBSTITUTE THE LOCAL CARGO CACHE. It is a FLOOR, not a census —
and it manufactures false findings, which I proved on this repo tonight.**
Reading `~/.cargo/registry/src/` gave liminal-server 13 versions **with `0.3.2`
absent**, which reads exactly like a §3 sequence hole. The registry shows **14
versions with `0.3.2` present**: the box had simply never fetched it. The cache
is authoritative for *what was downloaded* and for nothing else. It remains the
right instrument for **the published manifest of a version you already have**
(offline, no `403` exposure) — a different question.

**Yanked is not absent.** A yanked version stays in the index with
`"yanked": true` — that is how cargo avoids selecting it. Check the flag; do
not infer removal from a gap. **And it changes how you may PHRASE guidance:**
beamr `0.13.1` and `0.13.2` are yanked, so the honest form of "where is the
FIFO fix" is **"0.13.0, or 0.14.0 and later" — never "0.13.x"**, which names
two versions cargo will refuse to select.

### ★ The exhibit worth reading twice

Measured by Artemis Peach at the published `.crate` files — not the repo, not
a tag — with both arms present so the instrument discriminates:

```
beamr 0.12.0 published:  new_lifo=4  new_fifo=0   -> LIFO, starving
beamr 0.13.0 published:  new_lifo=0  new_fifo=4   -> FIFO, fixed
```

The fix commit `4aa58c4` flips `Worker::new_lifo()` to `new_fifo()` on all four
priority lanes. The **release** commit `0e7c060` is titled *"release: beamr
0.12.1 — FIFO owner pop ships to crates.io consumers."* **`0.12.1` is one of
beamr's two tags with no published version.** So a consumer told to upgrade to
`0.12.1` cannot resolve it, and a `^0.12` requirement resolves to `0.12.0` —
**the LIFO build the fix existed to remove.**

**⇒ The record of the fix reproduces the incident's own mechanism.** This is
why the reconciliation is a tracked defect and not a documentation chore: four
documents asserted a release, three of them agreed with each other, and only
the fourth — the artifact — was right.

### Build the denominator before taking the difference

**`publish = false` crates must be DROPPED from the denominator first
(Athena Zooper Dooper).** A declared non-participant is not an absence. Left
in, it reports as a permanent, unexplained *"published: never"* row that can
never be closed — and it makes the denominator wrong **in the direction that
hides real gaps**, because a reader who learns to skip the known-404 rows will
eventually skip a genuine one. **Enumerate workspace members, drop every
manifest setting `publish = false`, difference what remains, and state the drop
count.**

**Refinement, measured here: the drop is itself a two-document check, so take
it rather than waste it.** The manifest flag and the registry must *agree*, and
either disagreement is a real finding:

| Manifest | Registry | Reading |
|---|---|---|
| `publish = false` | `HTTP-404` | consistent — drop it, count it, move on |
| `publish = false` | **`HTTP-200`** | **something was published that declares itself unpublishable** — flag added after the fact, or a publish that should not have happened |
| publishable | `HTTP-404` | a genuine never-published crate; needs a ruling, not silence |

liminal: **5 workspace members, 1 dropped (`liminal-ts-wasm`, `publish = false`
at `sdks/liminal-ts/wasm-src`), denominator 4.** The registry returns
`HTTP-404` for it, so the two documents agree and the row closes. The four
publishable crates all resolve `HTTP-200`.

Registry read 2026-07-30, `User-Agent` set, both controls in-set. Tags from
this clone (`git tag` is complete in any clone; the registry side is not).

```

liminal-rs        (13)  0.2.0 0.2.1 0.2.2 0.2.3 0.2.4 0.2.5 0.3.0 0.3.1 0.3.2 0.4.0 0.4.1 0.5.0 0.5.1

```

- **DIRECTION 1 — published, untagged: 10 of 14 distinct versions.**
  `0.2.2 0.2.4 0.2.5 0.3.0 0.3.1 0.3.2 0.3.3 0.4.0 0.4.1 0.5.0`.
  ⇒ For most of liminal's history `git show <tag>:Cargo.toml` does not return
  a wrong answer, it returns **nothing** — and a seat under time pressure
  fills that gap with `main`, which is the reading that is definitely wrong.
- **DIRECTION 2 — tagged, never published: NONE.** All four tags correspond to
  published versions. **Stated as a measured clean result, not an omission:**
  it is the direction that would have been actively misleading, and "no
  instances" only means something if someone looked. (`liminal-v0.2.3` and
  `liminal-v0.5.1` have no `liminal-protocol` counterpart — that is the
  lockstep point below, not a Direction-2 instance.)
- **DIRECTION 3 — holes in the published sequence: NONE** within any minor
  series, every crate, `yanked` checked on all 45 entries. Athena's mechanism
  (`frame-cli` published `0.4.0` and `0.4.2`, never `0.4.1`, absent not
  yanked) does not reproduce here. **Carry that mechanism as LATENT, not as a
  live break: she measured that nothing in frame actually pins `=0.4.1`
  (`git grep` at both `origin/main` and the re-pin tip, zero hits, with a
  positive control on the same pattern). It earns its place on the false
  inference it enables — "0.4.2 exists, so 0.4.1 did" — not on damage done.**
- **THE FOUR CRATES ARE NOT IN LOCKSTEP.** `liminal-rs` has no `0.3.3`;
  `liminal-sdk` has no `0.2.5`; `liminal-protocol` has five versions against
  the others' thirteen or fourteen and skips `0.2.2`–`0.2.5` entirely.
  **⇒ There is no total order over the workspace, so a
  derive-the-tag-name-from-the-version shortcut cannot work either.**

**Not fixed, deliberately: the ten untagged releases stay untagged.** A release
marker is Tom's call, and back-dating one looks like tidying and reads later as
evidence. `CHANGELOG.md` carries the record; the tags do not.

## 4. What this costs, stated plainly

**Until the gate in the banner exists, "we pin X" is a statement about a
manifest, not about what resolves.** The estate's live example is liminal's
own: published `liminal-server 0.5.1` requires `beamr ^0.16.1`
(`>=0.16.1, <0.17.0`) — **observed at the published artifact, not derived from
a tag.** The day beamr `0.17.0` publishes and a consumer patches beamr to a
`0.17.x` checkout, that patch cannot satisfy `^0.16.1`, so cargo keeps a
registry `0.16.x` beside it: **two copies of beamr in one build, the tests
green against the patched one.** That prediction is only as good as the
requirement it rests on, which is why the requirement was read at the artifact.

`scripts/baseline-compare.py`, which is the same move one layer down — a pin
no runner mechanically compares is an instruction, not a control.
